# Digital Biotope（デジタルビオトープ）

食物連鎖のシミュレータ。どんなパラメータ・個体数比率なら生態系が釣り合うのかを、
ビジュアルを見ながら、あるいは総当たりで探索する。

パラメータをどう決めたか、何が壊れていてなぜ直したかは
**[docs/reports](docs/reports/)** にまとめてある。

## 動かす

```bash
npm install
npm run dev
```

http://localhost:5173 が開く。

- **構成** — 種の組み合わせを切り替える（下記）
- **スペースキー / 停止ボタン** — 再生・停止
- **速度** — 1フレームあたりのステップ数（1〜20倍）
- **シード** — 同じシードなら毎回まったく同じ結果になる
- スライダーは基本すべて**即時反映**。`*` 付き（初期個体数）だけリセット時に反映

グリッドは緑が濃いほど草が多い。同じセルに複数いる場合は上位の捕食者を優先して描くので、
個体数の少ない頂点捕食者も埋もれない。右のグラフは個体数の推移で、薄い緑の面が草の総量。

## 種の構成

いずれも 8000ステップ × シード5種で全種生存を確認済み
（[docs/reports/02](docs/reports/02-preset-validation.md)）。
ただし「4層」だけはシードを8種に増やすと1回崩壊する。上位捕食者を含む系は本質的に脆い。

| 構成 | 内容 |
|---|---|
| **基本（3層）** | 草 → 草食 → 肉食。約 690 / 400 で振動 |
| **競合（キーストーン捕食）** | 草食2種が同じ草を奪い合い、肉食は強い方だけを食べる |
| **雑食** | 雑食が草も草食動物も食べる。約 520 / 450 |
| **4層** | 草 → 草食 → 中位 → 頂点。約 760 / 390 / 130 のピラミッド |
| **追跡（視野あり）** | 草食が逃げ、肉食が追う。約 794 / 243 |
| **燃費（行動コストあり）** | 速度と視野に維持費がかかる。約 523 / 448 / 379 |

### 競合が面白い理由

草食A（強）とB（弱）は同じ草を奪い合うので、放っておくとAがBを競争排除する。
実際、肉食の初期個体数を0にしてリセットすると **Bは絶滅し、Aが1300近くまで独占する**。

肉食を入れるとAだけが捕食されて抑えられ、Bが生き残れるようになる（約 570 / 500 / 130）。
捕食者が競争の勝者を叩くことで多様性が保たれる、キーストーン捕食と呼ばれる現象。

### 雑食の閾値

雑食動物の**採食量が自分の代謝を超えると壊れる**。草だけで黒字になり、狩る必要が
なくなって草食動物を競争排除してしまうため。代謝0.7に対し、採食量0.8では3回中3回
草食が絶滅し、0.4では3回中3回共存した。既定は0.4で、草は餓死を防ぐ保険として働く。

### 4層の限界

頂点捕食者の代謝を下げすぎると餌に制約されなくなり、中位捕食者より個体数が多い
**逆ピラミッド**になる（代謝0.3で 935 / 208 / 220）。既定の0.55で正しい形になり、
0.65まで上げると頂点が絶滅する。生存できる幅が狭いのが最上位の特徴。

詳しい経緯は [docs/reports/01](docs/reports/01-coexistence-region.md) と
[02](docs/reports/02-preset-validation.md)。

### 視野と追跡

**視野** を1以上にすると、その種はランダムウォークをやめて

1. 捕食者が見えたら逃げる
2. 獲物が見えたら追う
3. 草の多い方へ寄る
4. どれもなければランダム

の順に動く。既定は0（ランダムウォーク）で、他の4構成はすべて0のまま。

追跡を成立させるには**2つとも**必要で、どちらを外しても共存しない。

- **速度差** — 等速だと逃げ切られて遭遇が一度も起きず、捕食者が必ず餓死する。
  捕獲成功率をいくら上げても、狩る機会そのものが無いので効かない
- **捕獲成功率 < 1** — 追跡が決定的なので、成功率1.0だと
  「速度が足りず永遠に捕まえられない」か「必ず捕まえて獲物を絶滅させる」の二択になる。
  速度2・成功率1.0では例外なく全滅した

既定は成功率0.04（25回に1回）。0.03では捕食者が絶滅し、0.06では4割の確率で共倒れる。

実装で3回壊した経緯は [docs/reports/03](docs/reports/03-vision-and-pursuit.md)。

### 行動コスト（燃費）

既定では速度も視野も無料で、「代謝は低いほど得」という歪みがある。行動コストを入れると
実際に減るエネルギーが次のようになる。

```
実効代謝 = 基礎代謝 + 速度コスト × 移動速度 + 視野コスト × 視野
```

両コストが0なら実効代謝＝基礎代謝で、他の5構成はすべてこの状態。UIの各種グループには
実効代謝が常時表示されるので、スライダーの「代謝」と実際の消費がずれても分かる。

「燃費」構成は**草食2種の違いを視野だけ**にしてある。警戒型（視野3）は捕食者を見て
逃げられるが実効代謝0.475、無警戒型（視野0）は逃げられない代わりに0.40で済む。

| 条件 | 警戒型 | 無警戒型 | 結果 |
|---|---|---|---|
| 肉食あり（既定） | 519 | 450 | 目が元を取る |
| 肉食なし | 477 | 1056 | 目は重荷 |
| 肉食あり・視野コスト0 | 937 | **0** | 無警戒型が絶滅 |
| 肉食あり・視野コスト0.18 | **0** | 1622 | 警戒型が絶滅 |

交差点は視野コスト0.025〜0.030の間にある。既定は0.025で、スライダーを一目盛り動かすだけで
勝敗が入れ替わる。

なお**捕食者がいないと視野は純粋な足枷になる**（コスト0でも 657 対 966 で負ける）。
草を探して動く個体は餌の多い場所に集まってしまい、そこで競争が激化する。
ランダムに散らばる方が結果的に草を広く食べられる。

詳細は [docs/reports/05](docs/reports/05-activity-cost.md)。

### 草地のパッチ（空間的不均質）

**パッチの強さ** を上げると、草の回復速度がセルごとに変わる。重みの平均は1に
正規化されるので、**世界全体の生産量は変わらず分布だけが変わる**。強さ0.9なら
最も痩せたセルで既定の0.1倍、最も豊かなセルで1.9倍になる。既定は0（一様）。

不均質にすると、振動の**山は変わらず谷だけが上がる**。痩せたセルと豊かなセルが
同時に草切れを起こさないため。谷の深さで生死が決まる系ではこれが効いて、

- 回復速度を4倍にすると崩壊していた基本構成が、8シードで生き残るようになる
- 4層の頂点捕食者が、代謝0.60（一様なら8シードすべてで絶滅）で生き残る

一方で**共存には逆に働く**。「燃費」構成の草食2種は視野だけが違うが、
捕食者のいない一様な世界では 657 対 966 だったものが、パッチを入れると
**16 対 1606** になる。単独で走らせるとどちらも同じ数（約1600）を養えるので、
これは競争の中でだけ出る差。草を探して動く個体は刈り残しが多く（2.54 対 0.53）、
パッチを入れるとそれが3.18まで増える。残した草は競争相手が食べる。

環境に構造を入れても、それを読む規則が噛み合わなければ多様性は増えない。
むしろ片方の効率を下げるだけの負荷になる。

詳細は [docs/reports/07](docs/reports/07-grass-patches.md)。

### 死骸の還元

**死骸の還元** を上げると、死んだ個体がその量だけ自分のいたセルの草に戻る。
既定は0（死骸は消える）。**食べられて死んだ個体は戻らない** — 体が捕食者へ
移っているため。

効く先は偏っている。下の層ほど食べられて死に、上の層ほど飢えて死ぬので、

| | 捕食死 | 餓死等 | 還元対象 |
|---|---|---|---|
| 草食動物 | 13.3 | 1.9 | 13% |
| 肉食動物 | 0.0 | 3.7 | 100% |

草食動物を還元してもほとんど効かない。系からエネルギーが本当に抜けるのは
**最上位が餓死したとき**で、ループを閉じるとは実質「捕食者の体を草に戻す」ことになる。

ただしこれは草の回復速度とは別口でエネルギーを注ぐ操作なので、
**総入力を揃えないと豊穣化と区別がつかない**。揃えて比べると、還元のほうが
同じエネルギーで壊れやすい（総入力975の還元は 4/8、それより多い986を一様に
入れると 8/8）。

効いているのは**空間の集中**。死骸は1セルに固まって落ちるので、そこだけ
採食量(4)の何倍もの山になる。**死骸の半径** を1にして9セルへ撒くだけで、
総入力も流入のばらつきも動かさずに 4/8 が 8/8 に戻る。

詳細は [docs/reports/08](docs/reports/08-corpse-recycling.md) と
[09](docs/reports/09-detritus-buffer.md)。09は08の機構の説明が誤りだった記録でもある。

### 種を足す

[src/core/presets.ts](src/core/presets.ts) に `animal({...})` を足すだけ。
捕食関係は `preys: [id, ...]` で書く。UIのスライダーもグラフの系列も種定義から
自動生成されるので、`ui/` 側は触らなくていい。

## パラメータ探索

```bash
npm run sweep
```

条件を総当たりで回し、結果を表示して `data/sweep.csv` に書き出す。
調べたい軸は [src/sweep/cli.ts](src/sweep/cli.ts) の `axes` を直接書き換える。

同じ条件をシードを変えて複数回試し、「全部生き残った回数 / 試行回数」を出す。
まぐれで共存した条件を弾くため。

CSVはBOM付きUTF-8。Excelでそのまま開ける。pandasで読むなら `encoding='utf-8-sig'`。

## モデル

NetLogo の Wolf Sheep Predation に相当する構成。

- **草**は地面の資源。セルごとに量を持ち、毎ステップ一定量ずつ上限まで回復する。
  エージェントではないので「草が絶滅する」ことはなく、食べ尽くされても再生する。
  回復速度はセルごとに変えられる（パッチ）が、既定では全セル同じ。
  死骸の還元を入れると上限を超えて積むことがある
- **動物**はエージェント。移動 → 捕食/採食 → 代謝 → 死亡 → 繁殖 の順で処理する
- 端は反対側につながる（トーラス）。壁にすると端に個体が溜まって分布が歪むため
- 捕食関係は種定義の `preys` で決まる。種を足せば連鎖が伸びる。
  シミュレーション側に種別の分岐は無い

1ステップの流れは [src/core/step.ts](src/core/step.ts) を読むのが早い。

### 挙動の目安

肉食動物の **代謝** と **捕食利得** の比が振動の激しさを決める。

| 条件 | 起きること |
|---|---|
| 利得が低い / 代謝が高い | 肉食が餓死して絶滅。草食は草の生産量で決まる上限に張り付く |
| 中間 | 個体数が振動する。草食のピークに遅れて肉食のピークが来る |
| 利得が高い / 代謝が低い | 肉食が増えすぎて草食を食い尽くし、共倒れ |

既定値（代謝 0.6 / 捕食利得 18）は、はっきり振動しつつ絶滅しにくい領域に置いてある。

草食動物の平衡個体数はだいたい `草の回復速度 × セル数 ÷ 草食の実効代謝` になる。
既定値なら `0.06 × 10800 ÷ 0.6 = 1080`。

この式のせいで**代謝を下げると振動が激しくなる**。4層で草食の代謝だけを下げていくと、
上限が上がるぶん増えすぎたときの跳ね上がりが大きくなり、草を刈り尽くして大量餓死する。
8シードで測ると振れ幅が 461-1604（代謝0.45）から 0-4063（代謝0.20）まで広がり、
0.20では半分が全滅した。絶滅はすべて300〜1100ステップの間、つまり**最初の一発**で決まる。

詳細と、これが「餌を増やす」形の豊穣化と同じかどうかは
[docs/reports/04](docs/reports/04-metabolism-stability.md) と
[06](docs/reports/06-enrichment.md) にまとめてある。

## 構成

```
src/
├── core/          # シミュレーション本体。DOM に触れない
│   ├── types.ts     # 種・環境の定義
│   ├── rng.ts       # シード付き乱数
│   ├── world.ts     # 状態（TypedArray）と空間インデックス
│   ├── step.ts      # 1ステップの進行
│   └── presets.ts   # 既定の種構成
├── sweep/         # パラメータ探索
│   ├── sweep.ts     # 探索エンジン・CSV出力
│   └── cli.ts       # 実行スクリプト（軸はここで定義）
└── ui/            # 表示
    ├── main.ts      # ループと操作
    ├── render.ts    # グリッド・グラフ描画
    ├── controls.ts  # 種定義からスライダーを生成
    └── style.css
```

`core/` は DOM を参照しない。表示側と探索側が同じコードを共有するため、
また将来 Web Worker に載せて探索を並列化するため。

### 性能

エージェントは Structure of Arrays（種別・座標・エネルギーをそれぞれ TypedArray）で
持つ。オブジェクトの配列より速く、Worker への転送もそのまま出来る。

セルごとの個体一覧は counting sort で毎ステップ組み直す。O(個体数 + セル数)。

手元の計測では 1000〜2000個体の構成でヘッドレス 10,000 ステップ/秒程度、
ブラウザで描画しながら 3,000 ステップ/秒程度。

視野を使うと1個体あたり (2r+1)² セルを走査するので明確に遅くなる。
同条件（草食約1000個体）での実測：

| 視野 | steps/sec |
|---|---|
| 0 | 9,800 |
| 1 | 4,500 |
| 2 | 2,700 |
| 3 | 1,800 |
| 5 | 880 |
| 8 | 390 |

視野を使う種の手番の前に空間インデックスを作り直すため、その構築回数も増える。

## やっていないこと

- **探索の並列化**（Web Worker）。現状は単一スレッド。36条件×3回×4000ステップで約37秒。
  視野ありの構成はこの5〜10倍かかるので、並列化の価値はこちらの方が大きい
- 種構成をUIから編集する機能。種を増やすには `presets.ts` を書き換える
- スイープの軸をUIから指定する機能。現状は `sweep/cli.ts` を書き換える
- 空腹度による行動変化。今は捕食者が見えている限り餌を探さないので、
  飢えていても逃げ続ける。「腹が減ったらリスクを取る」が入ると、
  速度差に頼らず追跡を成立させられる可能性がある
